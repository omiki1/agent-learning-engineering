# Agent 架构判断案例

先完成“你的设计”，再阅读每题后的参考分析。

## 通用答题模板

1. 是否需要 LLM？
2. 单次调用、Workflow、Agent 还是 Multi-Agent？
3. 哪些步骤确定，哪些允许动态决策？
4. Tools、State、Memory、权限分别是什么？
5. 停止、重试、HITL 和 Evaluation 如何设计？

## 案例 1：发票字段提取

上传发票 PDF，输出供应商、日期、金额和税号，并写入 ERP 草稿。

参考分析：OCR/解析→结构化抽取→业务校验是 Workflow；字段抽取可用单次 LLM Structured Output，不需要 Agent。写 ERP 是副作用，需幂等键和人工确认。指标是字段级准确率、解析失败率和重复写入率。

## 案例 2：开放式行业研究

用户要求比较一个新兴行业最近一年的技术与商业变化。

参考分析：适合 Workflow + Agentic Research 节点。固定范围确认、来源存储、引用验证和报告导出；动态搜索、Query Rewrite 和证据缺口判断。State 保存计划/证据/预算；偏好可进 Memory。按引用正确率、覆盖率、时效、成本评测。

## 案例 3：退款审批

读取订单、检查政策、决定退款并执行。

参考分析：政策与金额判断尽量确定性 Workflow。LLM 只分类非结构化原因或总结证据。退款工具必须逐用户授权、幂等、审批和审计。不要让 Agent 自主反复尝试退款。

## 案例 4：数据库分析助手

用户用自然语言询问销售趋势。

参考分析：Schema 检索→SQL 生成→只读静态检查→受限数据库→结果解释，可使用有限修复循环。Database credential 不给模型；禁止 DDL/DML；查询超时和行数上限。评 SQL 执行、答案和危险语句拒绝。

## 案例 5：个人学习助手

记住课程进度、偏好和薄弱点。

参考分析：进度/偏好用关系库长期记忆；当前练习用 State；历史答案不必全部进 Context。记忆写入需用户可见、可改、可删。推荐 Workflow，只有开放式辅导策略才用 Agent。

## 案例 6：软件修复 Agent

根据 Issue 修改仓库并运行测试。

参考分析：探索和修改可能需要 Agent；Git 状态检查、权限、测试、diff Review、最大循环是 Workflow。文件/命令工具需 workspace 和命令白名单或沙箱；合并/部署需要 HITL。评测试、回归、改动范围和危险命令。

## 案例 7：多语言客服

不同团队负责预订、退款和技术问题。

参考分析：先用一个 Triage + 专业工具/Workflow。只有权限、上下文和所有权必须转交时才 Handoff 到多个 Agent。不要仅因三个部门就复制三个相同 Prompt。

## 案例 8：每日固定报告

每天 9 点拉取三个 API，计算指标并发送固定模板。

参考分析：定时 Workflow，不需要 Agent。只有异常解释或自由文本摘要节点可能用 LLM。API 重试、数据质量、幂等发送和告警均确定性实现。

## 案例 9：企业知识问答

从政策、产品和技术文档回答员工问题。

参考分析：先做普通 Hybrid RAG；按文档权限过滤。只有多知识域选择、Query Rewrite 和补检带来可测收益时才 Agentic RAG。Resource 中的指令视作不可信数据。

## 案例 10：合同审查

标出风险条款、与标准模板比较并给修改建议。

参考分析：高风险辅助系统。解析/条款切分/规则比对为 Workflow，LLM 做分类与建议；必须保留原文引用、版本和律师 Review。不能把 LLM 输出当法律结论。

## 案例 11：多个独立研究员辩论

希望通过 5 个 Agent 辩论提高答案质量。

参考分析：先建立单 Agent 基线和独立检索/Reviewer。若 5 个 Agent 使用相同模型、Prompt、证据，观点可能高度相关，只增加成本。用消融实验验证独立性和质量收益。

## 案例 12：跨应用工具生态

同一组企业查询工具要被 IDE、客服助手和研究系统复用。

参考分析：适合 MCP Server，但每个 Host 仍需自己的 Agent/Workflow、用户授权、工具过滤和 Trace。按领域拆 Server，避免一个万能 Server。
